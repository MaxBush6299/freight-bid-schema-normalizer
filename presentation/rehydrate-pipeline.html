01  /  the problem we're solving

Pricing a customer bid is mostly mechanical data‑entry,
and one wrong cell can cost a contract.

A pricing analyst opens a blank bid template the customer has sent over. They open a priced lane export from RXO's own systems. Then they spend hours copying values across, one row at a time, while watching for a half‑dozen ways the two files don't quite line up.

The mechanics are tedious. The judgment that does matter (which export column belongs in which template cell, when to keep fuel separate, when to leave a lane out) gets crowded out by the act of typing. And the cost of a single mis‑mapped column shows up on every row of every lane.

03  /  how it works

Five stages, in order. Two of them never call an LLM.

The pipeline isolates the only place that benefits from an LLM (matching column names across files) and surrounds it with deterministic code on both sides. The match is checked against freight semantics before anything is written, and the approved mapping is cached so it is never proposed twice.

01 · profile
Read the template

Locate every bid‑sheet, find the header row, and enumerate which columns are writable vs locked. Fingerprint the template structure for the cache.

deterministic
02 · plan
Propose the mapping

The Foundry agent proposes which export field belongs in which template column. It does this once. Cache‑hit on a known template skips this step entirely.

Foundry · gpt‑5.4
03 · validate
Apply freight semantics

A deterministic post‑check demotes known anti‑patterns (all‑in → linehaul, categorical → numeric) to needs‑review before they can auto‑write.

deterministic
04 · verify
Human approves once

The analyst confirms the mapping in the wizard. Their approval is saved under the template's fingerprint and re‑used the next time the same template arrives.

human · cached
05 · write
Resolve & write

For each lane in the export, write into the matching template row, refusing to overwrite filled cells. Produce a per‑cell write report and a template diff proving only writable cells changed.

deterministic · auditable

Why the LLM lives only in step 2

Mapping "Customer Linehaul Rate" to "Freight Price" is a language task; arithmetic and file I/O are not. We let the model do the part it is best at, and keep code in charge of the parts where a wrong answer is worse than no answer.

Why the cache matters

A customer template doesn't change between bid cycles. Once an analyst has approved "this column comes from that field", there is no reason to ask the model again. The same cache also prevents subtle prompt‑drift from changing the answer run‑over‑run.

04  /  the validator

When the model is wrong, the validator catches it
before the file is ever written.

The all‑in‑rate vs linehaul‑rate confusion is the single most expensive mistake the pipeline could make. So it is the first thing the validator looks for, on every run, every mapping, every template, without asking the LLM.

A real run, against your file

The Foundry agent's first instinct on FTL LaneExport.xlsx was to map RXO All In Customer Rate into the template's Freight Price column. That looks right; both numbers are dollars. But the template's Total Shipment Rate is a formula that adds Fuel Surcharge on top, so writing the all‑in there double‑counts fuel on every lane.

The validator carries that rule deterministically. It demotes the mapping to confidence 0.40, marks it needs_review, and the writer refuses to auto‑write it, even if the operator approves everything else.

The number the customer actually expects

✕ if we'd trusted the LLM
$1,720.00

RXO All In Customer Rate, written into Freight Price. The template's Total formula then adds fuel a second time: $1,720.00 + $295.58 = $2,015.58. Wrong, by $295.58 on a single lane.

✓ what rehydrate writes
$1,424.42

Customer Linehaul Rate, written into Freight Price. Template's Total formula adds fuel once: $1,424.42 + $295.58 = $1,720.00, exactly the all‑in number on the source row.

The four rules the validator enforces today

all_in_to_linehaul
An all‑in / total / door‑to‑door rate cannot fill a linehaul / freight‑price column. The template's Total formula would add fuel again. Demotes to 0.40.
money safety
categorical_to_numeric
A categorical source (Equipment Type, Fuel Type, Currency, Mode, UoM) cannot fill a numeric Rate / Cost / Charge / Fee column. Demotes to 0.40.
type safety
numeric_to_categorical
A numeric dollar source cannot fill a categorical column. Demotes to 0.40.
type safety
identity_boost
When source and target column names are identical (e.g. Currency → Currency), boost to 0.95 so it passes the auto‑write gate without ceremony.
throughput

Adding a fifth rule is a code change, reviewed and tested. It is not prompt‑tuning. Anything the validator cannot decide falls through to the wizard, where the analyst makes the call.

05  /  verify & cache

Approve a template once. Every run after that is instant.

The Streamlit wizard is the only place a human sees the mapping. After approval, the plan is stored under the template's fingerprint and re‑used on every subsequent run, including across bid cycles, even months apart, as long as the template structure hasn't changed.

06  /  production‑ready

The things IT will ask about, answered up front.

Identity
Foundry agent runs in your tenant. Authentication via Microsoft Entra ID, no shared API keys checked into source. Tenant ID is pinned at process start so a stale corporate token can't be used by mistake.
in‑tenant
Data path
Customer files never leave the run host in demo mode. In the Function‑App deployment, files traverse blob containers you own (%EXPORT_CONTAINER%, %TEMPLATE_CONTAINER%, %OUTBOX_CONTAINER%) and are processed by your Function instance.
your storage
Preservation
Three‑layer guard refuses to overwrite a cell that already has a value. Pre‑filled customer inputs, descriptors, notes, and formulas are reported in write_report.json as skipped_preserved instead of being clobbered.
read‑only safe
Audit trail
Every run emits template_profile.json, mapping_plan.json, write_report.json, pending_review.json, and template_diff.json. The diff proves only writable cells changed. Every cell carries the source field that produced it.
replayable
Confidence gates
REHYDRATE_CONFIDENCE_THRESHOLD (default 0.70) sends low‑confidence mappings to the wizard; REHYDRATE_MIN_WRITE_CONFIDENCE (default 0.85) gates auto‑write. Validator‑demoted mappings (0.40) cannot pass either.
configurable
Cache invalidation
A cached plan is keyed by the template's structural fingerprint. Re‑arrange the sheets or change the writable‑column set and the fingerprint changes, the cache misses, the wizard re‑trains. The analyst can also force a re‑train with one click.
deterministic
Verified
137 unit tests covering the planner, validator, cache, resolver, writer, and runner. CI gates on test failure and on lint. The validator rules themselves carry 25 tests for the four anti‑patterns and the normalisation rules.
CI green
Deployment
Same code, two runtimes. Streamlit for analyst‑in‑the‑loop work today. Function App with an HTTP endpoint and an Event‑Grid blob trigger when you're ready to wire it into upstream automation. No code change between them.
portable
07  /  what's next

From this demo to production for RXO,
in four moves.

01
Pilot on three real customer templates ~2 weeks

Pick three live customers whose bid cycles you'd like to take off an analyst's plate. We profile each template, plan the mapping, your analyst approves once, and we measure the time‑to‑submission for the next cycle against today's manual baseline.

02
Wire into your file‑ingest path ~3 weeks

Swap Streamlit's local file picker for the Function‑App blob trigger. Customer templates land in %TEMPLATE_CONTAINER%; exports land in %EXPORT_CONTAINER%; finished submissions appear in your outbox. Analyst still holds the approval on first‑sight templates.

03
Shared, governed mapping cache ~2 weeks

Move the cache from local disk to your blob storage so an analyst’s approval is available to the whole pricing team. Add approval review: who approved it, when, and a one‑click rollback to the previous version of the mapping.

04
New validator rules from real exceptions ongoing

Every mapping an analyst rejects in the wizard becomes a candidate rule. We codify the recurring ones into the validator, so the next analyst (or the model) never sees that mistake again. The system gets smarter without prompt‑tuning.
